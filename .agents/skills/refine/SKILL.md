---
name: refine
description: Finish an existing project for launch by auditing its core flows, fixing defects, refining its presentation, and verifying the result. Use for a production-readiness or launch polish pass; preserve the existing project and its data contracts.
---

Work in the existing project. Infer the intended product and finish its core loop; avoid replacing working architecture or expanding into unrelated features. Decide ordinary implementation and design choices, record consequential reasons in the project documentation, and continue without requesting preference decisions.

1. Establish the baseline: inspect repository state and local instructions, read the README, product specification if available, source entry points and relevant implementation in full, and recent history. Identify storage formats, compatibility contracts and deployed behavior. Preserve unrelated local changes; create an isolated branch/worktree when needed. Run the project's actual install, tests and build commands. Record pre-existing failures and warnings separately.
2. Describe the product, core loop, unfinished work and a concrete plan. For visual products, capture baseline screenshots of all core screens at desktop and narrow mobile widths, with device emulation where required. Read the images. For CLIs/services, record equivalent observable requests and output. If blocked, record the exact limitation and continue independent work; never invent evidence.
3. Audit and fix in this order: crashes/data loss; broken controls/promises; privacy/data handling; platform/deployment essentials; core-loop gaps; onboarding, empty/error/recovery states, export/deletion where relevant, about/version; quality/accessibility; tests/docs. Preserve existing user data, URLs and integrations. Add meaningful compatibility tests before migrating persisted formats.
4. Refine presentation to fit the product and the user's requested direction. Improve hierarchy, spacing, responsive behavior, input/focus, contrast, reduced motion, performance and assets as appropriate. Prefer the existing stack. Custom assets must be original or have documented usable licenses and reproducible sources. Define budgets before expensive visual work; distinguish measured results from targets.
5. Work in reviewable stages. After each stage run relevant tests/build checks and re-render affected screens or exercise changed interfaces. Read the results rather than treating a successful build as proof of usability. Cover core flows, errors, persistence and supported input/render paths. Leave unavailable hardware/device tests explicitly unverified.
6. Review the complete final diff for regressions, no-op edits, unreferenced assets, data incompatibilities, secret exposure and development hooks in production. Update the README, asset inventory if used, owner checklist and project-specific agent invariants. Commit completed stages when the task authorizes repository changes.
7. Follow the project's existing deployment path and the user's authorization. When shipping is authorized, push the reviewed branch, verify its preview, then merge/push using the project's workflow. Verify the live revision and health. Do not substitute a working-tree upload for a git-connected deployment. If deployment or verification is blocked, retain the reviewable branch and report the blocker; do not label local work as shipped.

Report: live/preview URL and commit status; concrete fixes; visual or behavioral before/after evidence; generated assets and budgets when relevant; tests and unverified paths; remaining owner decisions and external blockers. Avoid transferring any source project's product-specific constraints to a new project.
